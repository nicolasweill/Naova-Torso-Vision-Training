TrainOnnxDet

Fine-tuning sim-to-real d'un modèle de détection ONNX (entraîné sur des données simulées RoboCup) sur le dataset TORSO-21 reality, avec suivi des expériences MLflow.

Python ≥ 3.10 PyTorch ≥ 2.2 ONNX Runtime onnx2torch MLflow Albumentations

Aperçu

Le projet prend un modèle ONNX de détection pré-entraîné en simulation (models/sim_data_det_0126.onnx), le convertit en module PyTorch avec onnx2torch, gèle une partie du réseau pour limiter l'oubli du domaine simulé, puis l'affine sur des images réelles de TORSO-21. Le meilleur checkpoint est ensuite réexporté en ONNX et publié comme artefact MLflow.

  • Entraînement : scripts/train.py, CUDA par défaut avec repli CPU.
  • Inférence : scripts/infer.py, fonctionne avec n'importe quel modèle ONNX de détection (YOLO-v5, YOLO-v8, SSD détectés automatiquement).
  • Suivi : paramètres, métriques par époque, artefacts et tags Git/hôte dans mlruns/.

Installation

pip install -e .

# Vérifier le montage sans entraîner (charge les données et le modèle)
python scripts/train.py --dry-run

Les dépendances sont listées dans requirements.txt et setup.py (torch, torchvision, onnx, onnxruntime, onnx2torch, mlflow, numpy < 2, opencv-python-headless, Pillow, albumentations, PyYAML, tqdm, pytest).

Inférence GPU

pip uninstall onnxruntime
pip install onnxruntime-gpu

Sans onnxruntime-gpu, l'inférence tourne sur CPU. Avec --device cuda et sans le provider CUDA, une RuntimeError est levée.

Format des labels YOLO, une ligne par objet, coordonnées normalisées dans [0, 1] :

class_id x_center y_center width height

Règles appliquées par Torso21Dataset :

  • Une image sans fichier label est ignorée (comptée comme « skipped » dans les logs).
  • Un fichier label vide est conservé : c'est une image de fond sans objet.
  • Les lignes mal formées, avec un class_id hors plage ou des coordonnées hors [0, 1] sont ignorées avec un warning.
  • Chaque image est passée en RGB puis redimensionnée en letterbox (ratio conservé, padding gris 114) vers input_size, et les boîtes sont recalculées en conséquence.

Pipeline

  1. Lecture des deux YAML et construction des dataclasses (TrainingConfig, LossConfig, AugConfig).
  2. Choix du device via get_device.
  3. Création de Torso21Dataset pour train et test (le split test sert de validation) et des DataLoaders (drop_last en train, pin_memory sur CUDA).
  4. Conversion ONNX vers PyTorch (load_model_for_training) et application de la stratégie de gel.
  5. Ouverture du run MLflow, journalisation de la config aplatie.
  6. Boucle d'époques dans Trainer.train() : warmup du LR, époque d'entraînement, validation, log des métriques, sauvegarde du meilleur checkpoint, pas du scheduler.
  7. Finalisation : rechargement du meilleur checkpoint, export best.onnx (opset 17, batch dynamique), validation avec onnx.checker, log du modèle dans MLflow (nom enregistré torso21-detector).

Sorties dans runs/<run-name>/ : best.pt (époque, poids, état de l'optimiseur, métriques) et best.onnx.

Stratégie de gel sim-to-real

_freeze_sim_domain_layers applique deux règles :

  • Les premiers freeze_ratio (70 %) des paramètres nommés ont requires_grad=False.
  • Toutes les couches BatchNorm2d sont gelées et maintenues en mode eval (y compris à chaque époque d'entraînement) pour préserver les statistiques du domaine simulé.

Seule la fin du réseau est donc entraînée, avec AdamW sur les paramètres encore libres.

Loss

DetectionLoss travaille sur les sorties décodées par DetectionHead :

  • Assignation : pour chaque boîte vérité terrain, la prédiction la plus proche par distance entre centres.
  • Boîtes : perte CIoU (IoU, distance des centres, pénalité de ratio), pondérée par box_weight.
  • Classes : BCE avec logits et label smoothing, pondérée par cls_weight.
  • Le terme obj est renvoyé à 0.
  • Si le format de sortie est raw (non reconnu), la loss vaut 0 avec un avertissement : l'entraînement ne converge pas.

Métriques

compute_map calcule l'AP par classe avec une interpolation à 11 points, sur les seuils IoU 0.50 à 0.95 (pas de 0.05). Valeurs journalisées à chaque validation :

Chaîne de traitement

  1. OnnxRunner.preprocess : BGR vers RGB, letterbox, division par 255, normalisation ImageNet, tenseur [1, 3, H, W]. La taille d'entrée est lue dans le modèle (640 par défaut si dynamique).
  2. OnnxRunner.run : exécution ONNX Runtime (CUDA puis CPU selon les providers disponibles).
  3. decode_outputs : détection automatique du format, sigmoïde, filtre de confiance, conversion en x1 y1 x2 y2, NMS par classe.
  4. Retour aux coordonnées de l'image d'origine (retrait du padding et de l'échelle), boîtes normalisées dans [0, 1].

Tests

pytest tests/
  • tests/test_dataset.py : letterbox et ratio, parsing YOLO (valide, vide, mal formé), découverte des paires image/label, types retournés, label vide conservé, image sans label ignorée.
  • tests/test_postprocess.py : NMS (meilleur score, boîtes disjointes, entrée vide), détection de format v5/v8/SSD, boîtes valides, seuil éliminant tout, format raw.

Aucun test ne couvre le Trainer, la loss ou les métriques.

Points d'attention

Constats issus de la lecture du code, utiles avant de comparer des runs ou de modifier le pipeline.

  • Loss simplifiée : l'assignation se fait par centre le plus proche, le terme de classe est construit à partir des scores décodés (marqué « placeholder » dans le code) et obj_weight n'a aucun effet.
  • Paramètres de config non utilisés : augmentation.random_scale_min/max et mosaic sont lus ou déclarés mais aucune transformation correspondante n'est appliquée. dataset.normalize_mean/std et image_extensions sont aussi codés en dur dans le code (stats ImageNet, extensions png/jpg/jpeg).
  • Validation sur le split test : le split test sert à la fois à choisir le meilleur checkpoint et à rapporter le mAP, ce qui rend le score optimiste.
  • Reprise partielle : --resume restaure les poids mais pas l'optimiseur, le scheduler ni le compteur d'époques.
  • Format de sortie du modèle : l'entraînement dépend de la détection automatique du format. Si elle retourne raw, la loss est nulle et le modèle ne s'améliore pas.
  • Boîtes décodées : DetectionHead renvoie des x1 y1 x2 y2, alors que DetectionLoss les traite comme cx cy w h pour la perte CIoU. À vérifier avant d'interpréter les courbes de loss.
  • Dry run : l'option charge les datasets et le modèle puis quitte après une passe avant ; aucun run MLflow n'est créé.
